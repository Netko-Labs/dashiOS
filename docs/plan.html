Release plan · build order

Dashi 0.4.0 plan

How 0.4.0 gets built: the recommended proposals from the 0.4.0 spec, in eight milestones, each with its work, the files it touches, and how it is checked before the next one starts.

◆

Only the picked proposals are here; the alternatives and their mockups stay in the spec. Where the spec left a choice of how to build something, this plan makes one and lists it under Choices this plan makes, so each can be changed before work reaches it.

How the release is run

  • One branch. Work lands on release/0.4.0, off main, as 0.3.0 did, with a commit at each checkpoint. tasks/todo.md gets one checklist per milestone, ticked as each item is verified.
  • The VM first. Compositor and shell changes are checked in the VM (vm/vm desktop, vm/agent), never by running the checkout's session on the laptop. The laptop gets 0.4.0 as packages once a milestone passes in the VM.
  • Hardware on the laptop, from the command line. What only real hardware can show (firmware attributes, the SMU, the graphics card) is checked by running dashi-hardware's CLI on the laptop, not the session. Each such step is listed and asked for before it runs.
  • One writer per knob. EPP, the platform profiles, the charge limit and the power limits each have exactly one owner (the mode recipe through dashi-hardware). tuned's Dashi profiles and asusd are configured to leave them alone.
  • Policy stays in TypeScript. New compositor requests draw or report; the shell decides (when an edge hold fires, which Desktop a window goes to, what a capture hides).
  • Docs in the same commit. docs/compositor-ipc.md with every IPC change (and test/ipc-contract.test.ts), docs/applets.md with protocol v2, design.html with any new measure.

1 · Power base and a lost card

Fix what broke on the laptop this week: power modes that exist, and a graphics card that can fall off the bus without hanging Steam's shutdown and every Chromium app.

Work

  • spin/rpm/dashi-release.spec: require tuned-ppd (and conflict with power-profiles-daemon). Power A
  • src/system/profiles.ts: talk to the power-profiles D-Bus API that tuned-ppd serves and watch ActiveProfile, instead of running the CLI. The mode row in Battery & Power and the battery menu shows on every machine that has modes.
  • src/graphics/lost-card.ts: follow the kernel log for NVIDIA Xid … 79 and pciehp "Link Down" on the card's own port, and say so once, plainly. Graphics F
  • src/gpu-env.ts: once the card is lost, stop offloading to it; PrefersNonDefaultGPU apps start on the integrated GPU, with a note.
  • src/shutdown.ts: give processes 10 s, then ask logind to power off or restart regardless of what is stuck in the driver.

Checks

  • test/lost-card.test.ts: the journal lines from 2026-11-03 and 2026-11-04 match; others with "Xid" or "Link Down" for a different device don't.
  • test/profiles.test.ts: the D-Bus property parsing, and the change signal moving the row.
  • VM: tuned-ppd installed by the release package, the mode row present and in sync with tuned-adm active. A fake loss written to /dev/kmsg as root shows the notice. Shutdown with a process stuck reading a FUSE file that never answers finishes in about 15 s.

Done when a fresh VM install shows power modes, a simulated card loss is announced and survived, and shutdown never waits on a stuck process for more than 15 s.

Separate and asked first: turning off D3cold for the card on the laptop (d3cold_allowed=0 through a udev rule), to see whether the drops stop. It changes the host's driver configuration, so it waits for a yes.

2 · dashi-hardware and power in sync

One privileged helper for everything a laptop's kernel exposes, a model database for what the kernel can't say, and one power mode that drives all of it, both ways.

The helper

  • crates/dashi-hardware: a Rust system service on the system bus (dev.dashi.Hardware1, D-Bus activated, its own systemd unit), with a polkit action per kind of change. Mode, charge limit and keyboard light are allowed for the active session; power limits, the Curve Optimizer and fan curves ask for the password once (auth_admin_keep). ASUS support C
  • Backends: firmware attributes (/sys/class/firmware-attributes/*, asus-armoury first), both platform profiles, charge_control_end_threshold, hwmon fan curves, cpufreq boost and amd_pstate EPP, and the SMU mailbox.
  • The SMU: the Curve Optimizer sent the way RyzenAdj reaches the SMU (PCI config space), with negative offsets encoded as 0x100000 + offset, all-core on MP1 0x4C and per-core on 0x4B. Available only when a zero write is accepted and kernel lockdown is off. CPU A
  • The helper clamps every value to the model database's range for this machine. The shell's ranges are for display; the helper's are the ones enforced.
  • A --sysfs-root option for tests, pointing the helper at a fake tree (the G14's, captured from the laptop) so the VM and CI can exercise it.

The model database

  • data/models/*.json, installed to /usr/share/dashi/models/, matched on DMI: fans, lighting, hotkey codes, quirks (D3cold), undervolt ranges, and the mode recipes. What the kernel reports always wins over the file. ASUS support E
  • The first entry is the GA403WR, with the attributes read on 2026-11-04 and "undervolt": { "cpu": [-40, 0], "perCore": true, "graphics": false }.
  • A laptop check (chassis type from DMI, a battery present) that the laptop-only rows and panes use.

Power modes

  • src/power/modes/: the mode store, a recipe per model (from the database, else tuned's defaults), appliers (tuned-ppd, firmware attributes through the helper, screen refresh through the compositor) and watchers. Power states A
  • Two columns per mode, plugged in and on battery; the cable switches columns, not modes. Power states D
  • Both ways: a change of platform_profile from Fn F5 or another tool shows in Dashi and pulls the rest of the recipe along, with a guard against write loops. Modes stay at three to match the key. Power states C
  • Automatic as the default: the mode follows the power source and battery level, a manual pick wins, and the battery menu says what Automatic chose and why, in one line. Power B
  • tuned profiles dashi-powersave, dashi-balanced and dashi-performance that leave EPP and the platform profile to the recipe, mapped in tuned-ppd's configuration.

Battery, keys and limits

  • Battery health: the charge limit, a one-time full charge, and an optional schedule, for any vendor with the kernel interface. A boot unit writes the limit again for firmware that forgets it. Power E
  • The keys: Fn F5 (mode), Fn F4 (keyboard light), the ROG key and mic mute become actions in keymap.ts, with the on-screen display that volume and brightness use. Keycodes come from the model database. ASUS support D
  • Power limits (SPL, SPPT, FPPT), boost and EPP with a battery frequency cap, and the graphics card's firmware limits (nv_tgp, nv_dynamic_boost, nv_temp_target) as helper methods. CPU B, C, E
  • The boot guard: a system unit counts boots. Tuning values are written at login, and again after waking, only after a clean boot; two failed boots in a row reset them. Anything that can freeze the machine applies with a countdown, as Displays does. CPU D

Where it shows

  • The battery menu as the hub: the mode, what Automatic chose, the charge limit. Laptop features A
  • A laptop row in Control Center: power mode and keyboard light now; graphics in 3; fans when ASUS Control provides them in 8. Laptop features B
  • Settings: Battery & Power gains modes, the charge limit and boost; Displays the panel overdrive; Keyboard the backlight. Laptop features C, CPU C
  • The Curve Optimizer, power limits and the card's limits get their sliders in ASUS Control's advanced view (milestone 8). In this milestone they are reached through the helper's CLI.

Checks

  • cargo test -p dashi-hardware: the SMU encoding (−5 is 0xFFFFB), clamping to the database's ranges, DMI matching, and each backend against the fake tree.
  • Shell tests: recipe resolution per column, Automatic's choices, and the both-ways guard (one key press makes one change).
  • VM, with the fake G14 tree: the battery menu, the Control Center row, the panes, a simulated Fn F5, a cable change, and the boot guard resetting after two failed boots.
  • On the laptop, from the CLI, asked first: read every attribute; set each mode and see both platform profiles follow; set the charge limit to 80 and reboot; the Curve Optimizer at −5 under stress-ng, then back to 0.

Done when Fn F5 and the battery menu always agree, unplugging switches to the battery column, the charge limit survives a reboot, and a bad tuning value can't outlive two failed boots.

3 · Graphics switching

The graphics card sleeps on battery, wakes when it's useful, and Dashi can say what is keeping it awake.

Work

  • spin/rpm/dashi-graphics.spec: package cardwire. It needs bpf in the kernel's lsm= list, which finish-install adds on two-GPU machines. It conflicts with supergfxctl and switcherooctl.
  • src/graphics/: the cardwire D-Bus client, the mode policy, and the holders list (cardwire's --lsof, else /proc/*/fd on the card's device nodes).
  • Automatic by default: Integrated on battery; Hybrid when plugged in or when a screen is connected to the card's ports. Apps already on the card are never pulled off; Dashi says once that it is waiting for them. Graphics D
  • "Using the graphics card" in the battery menu: each holder, its estimated draw, and Quit. Graphics B
  • The Graphics tile in Control Center's laptop row; its long press shows the three modes, the card's state and the apps allowed on it. Graphics A
  • A Graphics pane in Settings for the cards and the MUX switch (gpu_mux_mode, through the helper, applied at the next restart).
  • The lost-card watch from milestone 1 feeds the policy: a lost card puts the tile in a "Not responding" state and stops Automatic switching until restart.

Checks

  • Tests for the policy (power source, external screen, apps on the card) and the holders parsing.
  • VM (one GPU): cardwire absent leaves the tile and the menu section out, with no errors.
  • On the laptop, after the VM pass and with packages: Integrated on battery with the card in D3cold, Hybrid when plugged in, Steam on the card through Xwayland (the open question), and the holders list naming it.

Done when on battery the card is asleep with nothing on it, the battery menu explains any exception, and the laptop survives a lost card the way the VM did.

4 · Desktops, moving windows, the switcher

See Desktops, not just their names; drag windows between them from anywhere; and an app switcher that reaches windows. All of it rests on one new compositor feature: live, scaled pictures of windows.

Compositor

  • A thumbnail renderer in crates/dashi-comp/src/render/, shared by two requests: space-previews {output, rects: [{space, x, y, w, h}]} (each Space's windows and wallpaper, under the overview layer) and window-thumbnails {rects: [{window, x, y, w, h}]} (on the switcher's layer). Live while shown, cleared when the shell asks.
  • A move grab that survives space-switch, the held window going with it (wm/grabs/move_grab.rs, wm/space_list.rs).
  • An edge-hold {edge, output} event while a window is held against a screen edge for 400 ms.

Desktops

  • src/spaces/row.tsx: the row stays one line high and opens into thumbnails when the pointer or a dragged window reaches it. Desktops B
  • Names edited in place with metal-ui's input; spaces.names: (string | null)[] beside spaces.count in settings.ts. Desktops A's renaming
  • A Desktop with no name is called after the apps on it ("Helium, Terminal"). Desktops F

Moving windows

  • Drop on a Desktop's picture in Mission Control (src/overview/), and on the opened row. Moving A
  • Push against an edge: the shell's policy for edge-hold, only on edges with no screen beyond, never while a snap preview shows. Moving B
  • Carry it while you switch: the Desktop shortcuts and swipes work mid-drag. Moving C
  • "Move to" in the window's menu, built from spaces.names. Moving F

The switcher

  • src/switcher.tsx: windows kept per app; holding on an app shows its windows under the app row, with their badges. Switcher C
  • Typing filters apps and windows while ❖ is held. Switcher E
  • Q, H, M and W quit, hide, minimize and close while ❖ is held (the keys in keymap.ts for the switcher's session only). Switcher F
  • The panel grows by the window row; switcherSize learns it.

The share picker

  • dashi-share-picker, set as xdg-desktop-portal-wlr's chooser_cmd: it asks the shell to show the picker (the shell has the thumbnails) and prints the screen or window chosen, in the form the wlr portal reads. Portal G

Checks

  • cargo test for the grab across a Space change and the hold timer; the new requests in docs/compositor-ipc.md and test/ipc-contract.test.ts.
  • test/switcher.test.ts: grouping, filtering, step order. Tests for automatic names.
  • VM through vm/agent (it records mid-drag): open the row, rename, drag a window to an edge and hold, carry it with the shortcut, drop on a picture, the switcher's window row and actions, and sharing a window in Helium.

Done when every way of moving a window in the spec works in the VM, recorded, and the switcher reaches any window by keyboard alone.

5 · The Dashi portal

Every dialog GTK's portal drew is Dashi's, and xdg-desktop-portal-gtk is no longer installed.

The process

  • dashi-portal in the shell package: Bun, D-Bus name org.freedesktop.impl.portal.desktop.dashi, D-Bus activated through a user unit. dashi.portal lists FileChooser, Settings, Access, AppChooser, Inhibit, Print, Notification, Account, Email and DynamicLauncher.
  • Dialogs are Metal windows parented to the asking window through xdg-foreign (wayland: handles); X11 parents (x11:) are mapped to their window by the compositor. Each opens as a sheet on that window. Portal A
  • Prompts are drawn from a warm host, so a dialog opens as fast as a sheet in Dashi's own apps.

Interfaces, in this order

  • Inhibit, held in the shell, which decides what idle does, plus org.freedesktop.ScreenSaver for apps that skip the portal. Shown in the battery menu: what is keeping the screen awake. Portal H
  • Settings: color scheme, accent and contrast, and the org.gnome.desktop.interface keys GTK apps read.
  • FileChooser: opens on recent files and search (recents.ts, file-search.ts), then folders; open, save, folders, filters and choices. Portal C
  • Access: permissions as a sheet; apps with no window get a menu bar item that opens it. Portal D
  • AppChooser: Open With as a short list from default-handlers.ts, with "Always" and "Other…". Portal F
  • Account: name and picture, as a sheet, from src/accounts/. Portal J
  • DynamicLauncher: "Add to Dock" for web apps; the entry goes to ~/.local/share/applications and the Dock. Portal K
  • Print: a print sheet; jobs go to CUPS over IPP, from the PDF the portal hands over. Portal I
  • Notification into Dashi's notifications, and Email to the default mail handler: no new UI.

Removing GTK's portal, last

  • session/dashi-portals.conf: default=dashi; ScreenCast and Screenshot on wlr; Secret on gnome-keyring until milestone 6.
  • session/dashi-session: GTK_USE_PORTAL=1 and GDK_DEBUG=portals (Qt already uses the portal).
  • spin/rpm/dashi.spec: drop Requires: xdg-desktop-portal-gtk; install dashi.portal, the D-Bus service file and the user unit.

Checks

  • Tests per interface: request and response parsing, filter matching, MIME defaults, inhibit bookkeeping (an app that dies releases its hold).
  • VM with xdg-desktop-portal-gtk removed: open, save and Open With from Helium, Firefox, a GTK 4 app, a Flatpak and a Qt app; a video in Firefox keeps the screen on; printing to a CUPS PDF printer; "Add to Dock" from Helium.

Done when the image installs without xdg-desktop-portal-gtk, and every app in the VM matrix shows Dashi's dialogs.

6 · Secrets for agents

A vault that agents can use but never read, from Dashi or 1Password: they sign in, enter codes, use passkeys and pay within limits, and no secret ever reaches the agent's context or its pictures.

First: the vault and blanked captures

  • crates/dashi-secretd: a Rust system service with its own user. The vault is encrypted with a key unlocked at login through PAM and wrapped by the TPM where there is one. Callers are identified by pidfd and cgroup; anything in a dashi-agent-*.scope is refused. Secrets A
  • A small bridge running as you serves the Secret Service and the portal's Secret interface on the session bus, so apps keep working; dashi-portals.conf moves Secret to it and gnome-keyring goes. The login keyring is imported once, at the first login after the upgrade.
  • IPC capture-mask {client, rects | windows}; src/agents/run.ts applies it to every agent screenshot and recording: password fields (found through AT-SPI), the vault's windows and every consent sheet. Secrets H
  • Consent from the person only: the compositor marks input that comes from agent-input, and consent sheets ignore it.

Then: sign-in, codes, your turn

  • Agent tools in src/agents/tools/secrets.ts: list_logins (sites and account names only), sign_in, fill_code, hand_over. A new scope, "Sign in for you", in consent.ts. Secrets B, D, G
  • Filling: the field must be a password field (AT-SPI) on a page whose address matches the login's site; the value is typed by the broker and never returned to the agent.
  • Two sources: Dashi's vault and 1Password. The broker asks each enabled one for logins matching the site; the consent sheet names where each comes from, most recently used first. Settings › Passwords has a switch per source and where new logins are saved. Secrets I
  • The 1Password broker runs as you, outside every agent sandbox, and asks the 1Password app for one item per approved use (the CLI's desktop integration), then drops it.
  • One-time codes: TOTP computed in dashi-secretd, or read from 1Password; codes sent by email or text are left to "Your turn".
  • "Your turn": the agent pauses, a banner says what's needed, and Done hands back.

Then: passkeys

  • A virtual FIDO2 security key through dashi-hardware (uhid); dashi-secretd holds the keys and signs. Each use asks for the fingerprint reader or the password. Secrets C

Last: payments and the token proxy

  • pay, with a new scope "Pay for you" that "Always Allow" never covers. Limits per payment and per month; each payment needs the fingerprint or the password. Single-use virtual cards first, filled like a login; provider tokens (Stripe shared payment tokens, Visa Intelligent Commerce, Mastercard Agent Pay) where a merchant takes them. Secrets E
  • The token proxy in the agent sandbox: requests to listed hosts get their real credentials added on the way out, with a CA that only the sandbox trusts. The agent sees a placeholder. Secrets F

Checks

  • cargo test -p dashi-secretd: encryption, caller checks (an agent-scope caller is refused), TOTP against RFC 6238's vectors, CTAP2 messages.
  • Shell tests: the mask covers what it must, consent ignores agent input, logins listed without secrets, the source order.
  • VM, with a local test site served from the checkout (a login, TOTP, WebAuthn, and a Stripe test-mode checkout), never a real account: an agent through vm/agent signs in, enters a code, uses a passkey, pays a test amount, and its recordings show blanks where secrets were.
  • 1Password on the laptop, after the VM pass: one item per approval through the desktop integration (the open question).

Done when an agent completes the test site's sign-in, code, passkey and payment, and no secret appears in its transcript, its tool results or any capture it took.

7 · The applet SDK

Anyone can write an applet with real UI in an afternoon, and installing one from a stranger is safe.

Work

  • packages/applet (@dashi/applet): the client moved out of apps/kit/applet.ts, with reconnects, whole-state sends and typed messages; applet.json, the manifest, with its schema. SDK A
  • Protocol v2 in src/applets/protocol.ts and docs/applets.md: hello with the manifest first; popover and dismiss; nested menus.
  • Popovers drawn by the applet's own Metal host; the shell places them under the item and closes them. SDK B
  • The sandbox: src/applets/sandbox.ts runs each applet in bubblewrap with only what its manifest asks for; hardware through dashi-hardware's polkit actions, never raw sysfs; the consent sheet lists the permissions in plain words, once. Installed applets live in ~/.local/share/dashi/applets/<id>/. SDK D
  • The dev loop: dashi-applet new, dev (hot reload, a "dev" badge, the message log), pack and publish; dev runs against the VM through vm/agent. SDK E

Checks

  • Tests: protocol v1 applets still work; manifest validation; the sandbox's bubblewrap arguments per permission; popover placement at each screen edge.
  • VM: dashi-applet new weather to a working popover in the menu bar; an applet asking for a permission it didn't declare is refused.

Done when a new applet with a popover runs sandboxed in the VM from new to pack, and the existing tray and applets are unchanged.

8 · The Applet Store and ASUS Control

Applets install from one reviewable repository, and the first one does everything ROG Control Center does, and more.

The catalog

  • Netko-Labs/dashi-applets: one folder per applet; CI builds each from source, packs it, and publishes it as a release asset; CI builds the index. Store A, F
  • Signing: Dashi's key signs the index; the index lists each applet's author key; every update must be signed by that same key.
  • Publishing is a pull request. A pulled version is listed in the index, and the store disables it on machines that have it.

The store app

  • A new first-party app on apps/kit, shaped like Software and reusing its components: search, categories in a sidebar, compact rows, Installed and Updates. Store C
  • An applet's page: screenshots, what it can do in the manifest's words, whether it fits this machine, its source, and "Reviewed" for those Dashi's maintainers checked. Store E
  • Install, update and remove through the sandbox launcher from milestone 7; signatures checked before anything runs.

ASUS Control (Netko-Labs/asus-control)

  • The popover: one column of everyday controls with a live line (temperature, fan), then "Open ASUS Control". ASUS Control A
  • The window, shaped like Settings: fan curves you drag (8 points per fan), mode recipes (editing them is Power states B), keys, sensors, and the advanced view with the Curve Optimizer (with its countdown), power limits, boost and the card's limits. ASUS Control C, CPU A–E
  • Lighting, previewed: the lid's Slash bar drawn as it will play, its animation, brightness and when it shows; the keyboard's level and timeout. ASUS Control F
  • asusd packaged for USB lighting only, with its profile and charge-limit handling off, and installed on ASUS machines.
  • Fans in Control Center's laptop row, provided by ASUS Control.

Checks

  • CI in both repositories: build from source, sign, index; a tampered package or an update signed by a different key is refused by the store's tests.
  • VM, with the fake G14 tree: install ASUS Control from a test index, every pane, the countdown reverting a value.
  • On the laptop, with packages: fan curves, lighting, and a per-core Curve Optimizer search, one step at a time, with the boot guard in place (the open question of how far this chip goes).

Done when ASUS Control installs from the store on a fresh laptop install and covers every ROG Control Center feature the G14 has.

Choices this plan makes

Each is the plan's recommendation; any of them can change before its milestone starts.

ChoiceRecommendedWhy
How the shell reaches the helperA system D-Bus service with polkit per methodA mode change on every cable plug can't be a pkexec prompt; polkit lets everyday changes through and asks only for tuning.
The helper's and the vault's languageRustThey run privileged or hold secrets; the workspace already builds Rust and packages it.
Who enforces rangesThe helper, from the model databaseA bug in the shell, or an applet, can't write a value the machine doesn't take.
Applet popoversA layer-shell surface the shell grants to that applet while the popover is openPrivileged protocols are already granted per client by the shell; it answers the open question without a new Wayland role, if placement is exact enough.
Consent that agents can't clickThe compositor marks agent input; consent sheets ignore itagent-input can borrow the person's seat, so the sheet has to know where a click came from.
Secrets testingA local test site in the VM, Stripe in test modeNo real account or card is ever used while building.
Applet signaturesEd25519 (minisign's format)Small keys, a tool authors can install, and checks that are simple to write in the store.
Where asusd arrivesMilestone 8, with ASUS ControlNothing before that needs USB lighting; the kernel covers the rest.

Open questions, by milestone

  • 1 Does turning off D3cold for the card stop the drops, and what does it cost at idle? Tried only with a yes.
  • 2 Can asusd be kept off the platform profile and charge limit by configuration alone? (Matters again in 8.)
  • 3 Do cardwire's allow and block reach X11 apps through Xwayland (Steam)? Does Integrated let the card reach D3cold?
  • 6 What 1Password lets a desktop broker do on Linux: one item per approval through the app integration, without a service account.
  • 6 Which browsers report a page address Dashi can trust for sign-in, and keep DevTools closed to agents?
  • 7 Is a layer-shell popover from an applet's own host placed exactly under its item?
  • 8 How far can this chip go? The per-core search on the laptop, with the boot guard.
