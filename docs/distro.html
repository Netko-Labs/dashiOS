Distro spec

What Dashi is made of

Dashi is Fedora Linux 44 with its own desktop on top: a Rust Wayland compositor, a TypeScript shell on Bun, and a native UI drawn by mirin Metal. This page is the spec of the system, from GRUB to the first window.

The session

One login is one process tree. dashi-session picks the GPU, then starts the compositor with the shell as its client; the shell supervises everything else. When the compositor exits, the whole tree goes with it (its own process group, and PR_SET_PDEATHSIG).

dashi-session picks the GPU (dashi-gpu), logs to ~/.local/state/dashi/dashi.log └─ dashi-comp -c bun session.ts the compositor: screens, input, windows, Xwayland └─ bun session.ts the session supervisor (packages/shell/src/session.ts) ├─ bun main.tsx the shell: menu bar, Dock, sheets, services, policy │ ├─ mirin-metal-host one per surface: menu bar, Dock, overlays… │ └─ IPC ⇄ $XDG_RUNTIME_DIR/dashi-comp.sock (newline JSON) ├─ bun apps/settings … first-party apps: one Bun process + one Metal window each ├─ Xwayland started and restarted by dashi-comp └─ xdg-desktop-portal (gtk, wlr) · dashi-mcp for agents, with consent

Publishing to COPR

  1. Once: a Fedora account, logged in at copr.fedorainfracloud.org; the API token from /api/ in ~/.config/copr; copr-cli whoami prints the owner.
  2. Build every package from a clean, committed tree: spin/build-rpms all (in the VM). Each SRPM's spec carries its snapshot, so it rebuilds anywhere.
  3. spin/copr-publish (the project defaults to pejedev/dashi). It creates or corrects the project (the network on for Cargo; CachyOS, Helium, and RPM Fusion as extra repositories, as baseurls) and submits the newest SRPM of each package.
  4. Publish all of them together: dashi, dashi-comp, dashi-greeter, and dashi-live require each other at the exact same snapshot.
  5. Watch the builds. COPR builds in a clean root: a macro or tool the VM happens to have needs a BuildRequires.
◇

Open: Terra (Fyra Labs), already enabled as a repository, as a second home for Dashi's own packages. It needs specs written by hand under Terra's AI policy, and answers from Fyra on replacing fedora-release, RPM Fusion dependencies, and kernel packages.

Versions and releases

  • Release: Dashi's own number (0.1, 0.2…), shown as VERSION="0.2 beta". It is independent of Fedora's; VERSION_ID stays Fedora's (44) so Fedora tooling keeps working.
  • Snapshots: every package built from the tree is 0.2.0~beta.YYYYMMDD.HHMMSS.SHA, the commit's UTC date and time and its short hash, so two builds of a day sort by time (~ sorts before the final 0.2.0). Packages that track Fedora's number (dashi-release, -logos, -kernel, -nvidia) are version 44 with the snapshot as their release.
  • mirin: mirin-metal-host is 0.1.0~beta.YYYYMMDD.HHMMSS.SHA of the mirin commit it was built from; /usr/share/dashi/MIRIN_COMMIT records the one the shell was built against.
  • Build identity: DASHI_BUILD in os-release is the snapshot, so a bug report can name the exact tree.

The image

One live ISO, Dashi-0.2.0-x86_64.iso, made by spin/build-image (livemedia-creator) from spin/image/dashi-live.ks. It boots BIOS and UEFI, starts straight into a live session, and installs from there.

  • Default boot entry: "Test this media & start Dashi 44" (checks the medium with checkisomd5, then boots).
  • Boots to graphical.target; greetd's first session logs in liveuser automatically.
  • Installing copies the live system, so the installed system boots exactly what the image showed.
  • Before an image is called done, it is booted in QEMU with a plain virtio-vga (no 3D) through the default entry, all the way to the desktop.
