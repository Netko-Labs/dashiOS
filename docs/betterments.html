A launcher that beats Raycast

Tap ❖ today and you get a box that finds app names. Dashi owns the compositor, every window, every app's menus, every setting, the vault and an agent stack with typed tools, and the launcher uses none of it. This page is the plan to change that: not a copy of Raycast, but the launcher only an OS can build.

◆

Nothing here is picked yet. Cards outlined in green are the recommendation; "Today" marks what Dashi does now. On 2026-11-05 five reviewers each roasted the launcher from one point of view, with the code (release/0.4.0 at 7e49821) and VM screenshots (light mode, 1646 × 937): a keyboard-first power user, a visual and interaction designer, a platform and extension architect, an AI and agent-native product designer, and a newcomer, accessibility and copy reviewer. Their reports are in docs/launcher-roast/; every finding cites path:line under packages/shell/src/ unless it says otherwise. Picks to make are at the end.

Where Raycast wins, where Dashi wins

Honestly: today Raycast wins at nearly everything a launcher does. Dashi doesn't win anything yet; it holds pieces no app on someone else's OS can hold. The Raycast column is from its manual and changelog, as cited in the reports.

Raycast, today

  • Ranking that learns: fuzzy matching, frecency per query, Reset Ranking (search bar).
  • An action list on every item, each with its shortcut, searchable (action panel).
  • Aliases and a hotkey per command, fallback commands when nothing matches (fallbacks).
  • An extension store with a React API, deep links per command, script commands in any language (deeplinks).
  • AI from the root search: ⇥ for a quick answer, chat for follow-ups, MCP servers, a model picker, your own keys, local models (AI, 1.98).
  • Clipboard history, snippets, quicklinks, a calculator with units, currency and time zones.
  • Polish: smooth resizing, match emphasis, the keys shown for every action, an onboarding flow.

Dashi, because it is the OS

  • Windows are native. The compositor knows every window, its Desktop and its state; switching and thumbnails need no permission and no add-on.
  • Every setting is first-hand. A row can be the Wi-Fi switch, not a link to it, because the shell owns Settings and Control Center.
  • Menus are published, not scraped. Apps hand the shell their menus with shortcuts (app-menus/); thousands of commands exist on day one.
  • One typed catalog for people and agents. 71 tools with checked arguments (agents/tools/) can be the person's commands too, with the same consent.
  • Consent only a person can give. The compositor knows whether a press came from the person (agents/person.ts); secrets are typed, never shown to a model.
  • No server in the middle. Raycast routes its users' own keys through its servers (except OpenRouter); Dashi has no server to route through.
  • Extensions that can't hurt you. Applets are signed, sandboxed (bubblewrap, a D-Bus proxy) and declare permissions; Raycast's extensions get full Node.js.
  • Clipboard and text at the compositor, with AT-SPI and the vault to leave password fields out.

An action
  • Fields: address, title, keywords (per language), kind (open, toggle, run, pick), an argument schema (JSON Schema, as MCP already uses), scope, readOnly, destructive, who (person, agents, both), source. parse() stays: the launcher validates arguments live with it, so "vol 300" says "volume must be 0–100" on the row.
  • Sources on day one: apps and their [Desktop Action] groups (entries.ts:43 starts reading them), open windows, every setting (the settings registry from the app roast), the published menus of running apps (AppMenuStore.byPid, menusOf), Dashi's own menu rows (Lock Screen, Restart…), tray and applet menu rows.
  • Menus as commands: rows read "Notes › File › New Note" with the item's shortcut on the right, so choosing one teaches the key. Choosing sends the menu's own select; items marked agents: false are still offered here, because the launcher is the person.
  • Same consent: a person's command runs as the person, logged as "you". A command that asks agents every time (force_quit_app, trash_file) also asks a person, with its own sheet.
A dashi:// address for everything
  • dashi://settings/appearance/dark-mode, dashi://app/dev.dashi.notes/menu/new-note, dashi://applet/dev.example.weather/refresh?city=Lisbon, dashi://window/w3.
  • Registered as x-scheme-handler/dashi beside the first-party desktop entries, so xdg-open, a note or a help page can point at one exact place. Every row has Copy Address.
  • A settings address opens the pane scrolled to the row and highlights it. A link from outside never runs a destructive action: it opens the action with its arguments filled in.
Applets contribute commands
  • applet.json gains commands: [{id, title, keywords, args?, mode}], with mode instant, pick or view. Static, so they are indexed before the applet ever runs.
  • Protocol v3 adds run (shell to applet, with a seq), result (text, copy or open) and items (rows for pick mode, drawn by the shell, never applet pixels). view reuses the popover's Metal surface in the result area.
  • The consent sheet adds one line ("Adds 3 commands to the launcher"). Commands run in the applet's sandbox. A third-party row can't wear a Dashi glyph or a first-party name and never outranks an exact app or setting match; each row says where it came from ("Weather").

Agents in the launcher Done

Dashi's agent stack is serious work: a yes counts only when the person pressed it, secrets never reach the model, password fields are blank in captures, agents run in a sandbox. It is reachable only from a terminal (dashi-agent claude), and the launcher doesn't know an agent exists. The rule from the agents review stands over everything here: no model sits between "ter" and Terminal.

Everything the OS can do, two keystrokes away, answered in the row, in your words, and shared with your agents under your consent.
