Power modes are missing

Neither power-profiles-daemon nor tuned-ppd is installed, so Battery & Power leaves its power mode row out (system/profiles.ts), and nothing drives the two platform profiles. The firmware sits at Balanced forever. 0.4.0 fixes the base before it adds anything.

The graphics card fell off the bus

Twice in two days (2026-11-03 23:42, 2026-11-04 16:59): pciehp "Link Down", then NVIDIA Xid 79 while Steam used the card. Steam hung in the kernel, Chromium apps (T3 Code, 1Password) froze probing the card, and shutdown hung on an unkillable process. The likely trigger is fine-grained runtime D3cold. 0.4.0's graphics work has to notice a lost card and survive it.

Graphics switching with cardwire

cardwire (Open Gaming Collective, supergfxctl's successor) blocks a GPU with eBPF LSM hooks instead of unbinding it: the card stays bound, apps that open it get ENOENT, and switching needs no logout. Modes are Integrated (the graphics card is hidden), Hybrid (both), Smart (hidden unless an app is allowed) and Manual. It has a D-Bus service (org.opengamingcollective.cardwire) with per-app policies, battery and external-display auto-switching, and it restarts nvidia-powerd when the mode changes. Dashi already routes apps to one GPU (gpu-env.ts); cardwire makes the other one sleep for real.

FWhen the card is lost

Dashi watches the kernel log for Xid 79 and the PCIe link going down, says so plainly, stops starting apps on that card, and restarts without waiting on processes stuck in the driver.

  • The 2026-11-04 failure, handled
  • Shutdown no longer hangs
  • Reading the journal needs care
  • A stuck process can only be skipped

Recommendation: D by default, with A, B and F. Automatic switching is the default, Control Center shows and overrides it, the battery menu names what keeps the card awake, and a lost card is handled (F) before anything else ships. C rides on cardwire's Smart policies later; E is the Settings home for the MUX.

Build
  • Package cardwire (and its BPF LSM requirement: lsm=…,bpf on the kernel command line) as dashi-graphics; installed by finish-install on two-GPU machines. It conflicts with supergfxctl and switcherooctl.
  • src/graphics/ in the shell: the cardwire D-Bus client, the mode policy (power source, external screens), the holders list, and the lost-card watch (journal: NVRM: Xid … 79, pciehp "Link Down" on the card's port).
  • Lost card: gpu-env.ts stops offloading to it; the shutdown path (shutdown.ts) gives stuck processes 10 s, then asks logind to reboot regardless.
  • Separately, on this laptop: try disabling D3cold for the card (d3cold_allowed=0, a udev rule) and watch for drops; if they stop, ship it in dashi-nvidia for this model.
Open
  • cardwire says it is Wayland-only and early (breaking changes). Steam is an X11 app here: check that its block and allow work through Xwayland before shipping.
  • Does Integrated mode let the card reach D3cold, the state it failed to wake from?

CPU tuning and undervolt

On AMD, undervolting means the Curve Optimizer: an offset that the SMU firmware applies to every core's voltage curve. It does work on the HX 370 (Strix Point). Earlier reports of it being "refused" came from tools passing −2 as a 32-bit 0xFFFFFFFE, while the SMU expects a 20-bit value (0x100000 − 2). G-Helper encodes the value this way on Windows, and ROG Control's fix was tested on this model and BIOS.

Tested on this laptop, 2026-11-04: GA403WR, BIOS 312, RyzenAdj 0.19.0 over PCI config space, no ryzen_smu --set-coall=-5 rejected by the SMU (the 32-bit form) --set-coall=1048571 accepted (0x100000 − 5) stress-ng, 24 threads, matrixprod --verify, 60 s, plugged in, Balanced: offset 0 91.9 °C 60.1 W 3429 MHz offset −5 92.1 °C 59.0 W 3368 MHz 13 036 ops/s 0 failures offset 0 again 92.2 °C 57.2 W 3344 MHz 13 060 ops/s Set back to 0 afterwards (the SMU forgets the offset at reboot anyway).

At −5 the difference was within run-to-run noise: the chip sat at its 92 °C limit in every run. G-Helper's range is −40 to 0, set for all cores or per core (MP1 0x4C and 0x4B). Strix Point has no graphics offset. The SMU forgets the offset at reboot. Sending it needs PCI config writes, which kernel lockdown blocks, so it doesn't work with Secure Boot on.

The applet SDK

Today an applet is a process on $XDG_RUNTIME_DIR/dashi-applets.sock that sends a glyph, a label and a one-level menu (applets.md), with a small client in the app kit (apps/kit/applet.ts). That's enough for a timer, not for ASUS Control. The SDK turns it into something people can build, share and trust.

// applet.json

  "version": "0.1.0",
  "dashi": ">=0.4",

  "when": { "vendor": "ASUSTeK COMPUTER INC." },
  "permissions": [
    "hardware.power", "hardware.lighting",
    "dbus.system:xyz.ljones.Asusd", "notifications"

  glyph: FAN, label: (s) => s.mode,

System dialogs: a Dashi portal

When an app asks the desktop for a file, the color scheme, a permission, the "Open With" list, a printer, or to keep the screen awake, it asks xdg-desktop-portal, which hands the request to a backend. Dashi has none of its own (session/dashi-portals.conf): GTK's backend answers everything but screen sharing, so those dialogs are GNOME's, not Dashi's. Keeping the screen awake likely does nothing, because GTK's backend passes it to org.gnome.SessionManager, which Dashi doesn't run. In 0.4.0, xdg-desktop-portal-dashi serves every interface GTK's did, and xdg-desktop-portal-gtk leaves Dashi's dependencies. Screen capture stays with the wlroots portal (not GTK), with Dashi's picker in front of it.

  • Apps that would draw their own dialog are pointed at the portal in dashi-session: GTK_USE_PORTAL=1 (GTK 3, Firefox) and GDK_DEBUG=portals (GTK 4).   • Inhibit is held in the shell, which decides what idle does: while an app holds it, the shell doesn't blank, lock or sleep. dashi-comp's idle-inhibit protocol already covers a visible Wayland surface; this covers apps that ask through D-Bus, and asks made while the window is hidden. org.freedesktop.ScreenSaver is served as well, for Firefox, mpv and others that skip the portal.
  • The share picker is dashi-share-picker, set as the wlroots portal's chooser_cmd. It prints the output or the window the person chose.
  • Tests: request and response parsing for each interface, filter matching, mime defaults; the dialogs and parenting in the VM with Helium, Firefox, a GTK 4 app, a Flatpak and a Qt app, with xdg-desktop-portal-gtk uninstalled.

Secrets for agents

Today, gnome-keyring hands any password to any program running as you: an agent in a terminal can run secret-tool lookup and read everything. An agent driving the screen through dashi-mcp sees whatever is on screen. Dashi's agent layer already has scopes, consent sheets, "Always Allow" grants per agent, an activity log, and screenshots that wait until no consent sheet is showing (src/agents/). The goal is a store whose secrets agents can use (to sign in, confirm a person, pay) but never read.

The rules

A secret never enters an agent's context: not as text, a picture, a file, or an environment variable. Each use is approved on a sheet only the person's seat can answer, scoped to the task, and logged. Where possible the agent gets something that is useless anywhere else: a passkey signature, a single-use card, a token that only works for one host.

What this can't fix

Once signed in, the agent acts as you on that site until the session ends. An agent with DevTools access to a browser (CDP) can read field values and cookies, so filling is safe only in a browser the agent drives through the screen. A program outside the agent sandbox with ptrace rights could read another process's memory, which is why the vault runs as its own user.

IDashi and 1Password, both

Both are sources, and each can be turned on in Settings › Passwords. When an agent asks to sign in, the broker looks in both and the consent sheet names where the login comes from. 1Password items are read through its desktop app integration and go straight into the field. New logins are saved wherever you choose. Dashi's vault always holds app secrets (the Secret Service), passkeys and API tokens. Bitwarden can be added the same way.

  • No migration for 1Password users
  • Use whichever vault has the login
  • The same login can live in both
  • 1Password's Linux API sets the limits

Picked: all of it in 0.4.0, with Dashi's vault and 1Password both supported (I). Build in this order: the vault and blanked captures (A, H), because nothing else is safe without them; then sign-in with one-time codes (B, D) from either vault, and "Your turn" (G); then passkeys through a virtual security key (C); then payments with limits (E) and the token proxy (F). Dashi's vault replaces gnome-keyring for apps; logins, codes and cards can come from either vault, whichever is more convenient.

Build
  • dashi-secretd: a system service with its own user. The vault is encrypted with a key unlocked at login (PAM) and wrapped by the TPM where there is one. It serves the Secret Service and portal Secret to apps, with agents' cgroups filtered out, and a private socket for the shell's tools.
  • Agent tools in src/agents/tools: list_logins (sites and account names only), sign_in, fill_code, pay, hand_over. New scopes "Sign in for you" and "Pay for you", which "Always Allow" never covers for payments.
  • Consent sheets accept only the person's seat, never agent-input; payments and passkeys need the fingerprint reader or the password.
  • IPC: capture-mask {client, rects | windows} for agent captures (H); run.ts applies it to every agent screenshot and recording.
  • The virtual FIDO2 key goes through dashi-hardware (uhid). The proxy runs in the agent sandbox, with a CA that only the sandbox trusts.
  • Sources: the broker asks each enabled vault for logins matching the site and lists them in the consent sheet with where each comes from. When both have one, the most recently used login is listed first. 1Password: a broker process running as you, outside every agent sandbox, asks the 1Password app for one item per approved use (the CLI's desktop integration, or 1Password's SDK), types it in, and drops it. Agents can't reach the broker's socket or the 1Password app's.
  • Payments: single-use virtual cards first (any issuer that offers them, filled by B), then a provider token (Stripe shared payment tokens, Visa Intelligent Commerce, Mastercard Agent Pay) where the merchant takes one.
