Release plan · build order

Dashi 0.5.0 plan

Everything 0.4.0 left undone, in four waves: the platform pieces first, then the apps' big ideas built on them, then the launcher's and agents' leftovers, then the design rules the code doesn't follow yet. Real hardware and live services are checked alongside.

◆

The picks were made on 2026-11-06: every recommendation, except KDE runners, which are left out. Each item has a one-line why, where it lands, a size (S a day or less, M a few days, L a week or more) and where it came from: a roast report (docs/roast/), a Launcher row, a Proposals card, a design rule, or 0.4.0's known issues. The picks are at the end.

How the release is run

  • The owner picks first. No wave starts until its picks below are made.
  • One area at a time. As in 0.4.0, each area is built on its own branch off release/0.5.0, reviewed in the VM on video (chapters and stills beside it), and merged only once the owner has seen it.
  • The VM first. Compositor and shell changes run in the VM, never in the laptop's own session. The laptop gets them as packages.
  • Docs in the same commit. A rule that becomes true drops its "Not yet in code" tag in design.html, citing the file.

Wave 1 · Platform foundations

Why first: every big idea in Wave 2 stands on these. Editor's document surface and Notes' live page need a caret and a selection; Files needs ⇧-click and ❖-click; every app needs Undo, a focus model and a close that asks. Built once in mirin and @dashi/ui, they land in every app at once; built per app, they'd be built ten times.

Picks

Made on 2026-11-06. The pick is marked.

  1. The order of the waves. Picked as written: platform, apps, launcher, rules. Or launcher first, since it's what people touch most; but its leftovers are small, and the apps wait on Wave 1.
  2. Where the text model lives. Picked in mirin's TextInput, with a document view on top for Editor and Notes. Or a Dashi-only editor component; but every field would miss out.
  3. How a close asks. Picked a close request mirin hands to the app, which may hold the window open to ask. Or the shell asks for every app with a running child; simpler, but it can't know about unsaved text.
  4. One file browser. Picked Files' core as a component, embedded by the portal, dashi-dialog and the apps. Or the portal opens Files itself in a sheet; less code, but a second process per dialog.
  5. The Applet Store. Picked fold it into Software as a section. Or keep two apps with one trust language.
  6. Text size. Picked every Dashi window follows it, through @dashi/ui's type scale. Or the launcher and GTK apps only, as now.
  7. KDE runners. Picked leave them out until someone asks: few people run KDE apps on Dashi, so nothing would show. Or in Wave 3, read-only behind the registry, as search providers are.
  8. D3cold for the graphics card. Picked try d3cold_allowed=0 on the laptop until the next reboot. Done; see Verification.
